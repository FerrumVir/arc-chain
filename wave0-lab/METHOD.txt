WAVE 0 LAB - METHOD (for Astra's concurrence; throwaway branch wave0-v0712-lab, never merged, no PR, main untouched)

This branch is main at b26f9739 (the merged #159) plus the files under wave0-lab/ and two workflows. A guard job in
both workflows proves the tree is exactly that: base tree d5ecb735 plus ADDED lab files, nothing modified or removed.
The workflows are test-only: read-only token (contents, actions), no secret, no environment, no release, no tag.
All actions are SHA-pinned to the ones the repository's own workflows already use.

WHAT IT PROVES, IN TWO STAGES

against the launcher bytes of handoff artifact 11534092076 (run 37741303661), not CI-built ones. Every job downloads
the artifact itself and checks its digest (sha256:d1f58392...) and all five launcher digests before use, hashes the
launcher file before and after the harness, and writes a record. A summary job writes stage-a-summary.json.
  linux-x86_64   headless acceptance (systemd, real v0.7.11 updater)   and  desktop acceptance      ubuntu-24.04
  windows-x86_64 desktop acceptance                                                                  windows-latest
  macos-arm64    desktop acceptance                                                                  macos-15

  --dry-run-evidence accepts the summary only if all five final digests are CONSUMED with PASS (aarch64: the named

Stage B (workflow wave0-lab-soak.yml, runs on the same push; separate concurrency group): the soak, entirely inside a
nested KVM x86_64 Ubuntu 24.04 VM on a hosted ubuntu-24.04 runner (QEMU, qcow2 disk, cloud-init, ssh forward).
  1 baseline   the unmodified v0.7.11 installer installs the pinned v0.7.7 node as a systemd service with the real
               arc-updater timer - the repository acceptance script's own setup, with the live network rejected.
  2 consume    scripts/legacy-bridge/canary-consume.sh --tag v0.7.12 --expect-sha256 41d92a47...: dry run, then
               --apply. Published mode (post-G0) runs the script UNMODIFIED against the real release. Artifact mode
               (pre-G0) is a REHEARSAL: the same script with its single download line replaced by a copy of the
               Stage A launcher bytes; the verdict says so and is never the post-G0 Wave 0.
  3 interrupt  an inbound byte quota (iptables) cuts the first uncached 29 MB node download mid-way; the v0.7
               30-second health logic rolls the launcher back (v0.7.7 returns); the network is restored; the next
               run must resume the .partial by Range (proved by the inbound byte count) and bring the node up.
  4 battery    real arc-updater run twice (state unchanged: binary, version.txt, pid, process start, identity, legacy
               data; exit status 22 before the Latest flip is recorded as information and labelled expected), three
               kickstarts (same identity, verified cache reused), then a REAL guest reboot (boot id changes, the node
               recovers by itself - the orchestrator issues no start command after it, audited in commands.jsonl,
               updater timer active, pre- and post-boot logs, >= 10 min healthy samples).
  5 soak       a guest service (enabled, observer only) writes one JSON sample per 60 s across the reboot. The run
               lasts until BOTH hold: >= 2 h uninterrupted after the last forced event (>= 121 samples) and >= 4 h
               since the first healthy bridged sample.
  6 invariants one node, stable identity, stake 0, compute off without consent or model, unchanged legacy-data
               hashes (BEFORE = the ExecStartPre snapshot at the start of the kept run, AFTER = end of soak),
               privacy-safe registration (public name node-<first 8 hex of the address>), unit files unchanged.
  7 stop       systemctl stop is clean, --legacy-bridge-rollback restores v0.7.7 on its untouched data, re-bridging
               keeps the identity, then the node is stopped. The job ends with the node stopped.
  Evidence: samples.jsonl, events.jsonl, commands.jsonl, checks-live.jsonl, invariants-before/after.json, guest logs
  (the v0.7 seed redacted), then evaluate_stage_b.py writes checks.json, verdict.json, REPORT.md: every check PASS or
  FAIL. The job fails on any FAIL. full profile: timeout 350 min, orchestrator deadline 315 min. smoke profile
  (about 40 minutes, 10 s samples) exercises every path but can never yield WAVE0_PASS.

DEVIATIONS AND LABELS (all recorded in the evidence)
  * REBOOT is real (guest reboot under KVM), not a stop/kill/cold-start substitute. It reboots a VM, not field
    hardware: boot ID, systemd ordering and unit enablement are real; firmware, disk and NIC are virtual.
  * Network: the guest reaches the Internet through QEMU user-mode NAT with IPv6 off. The live network is opened to the
    bridged node only when stage_b.live_network is "allowed" (the recorded authorization: one stake-0 test node,
    compute off, separate clean environment); the v0.7.7 baseline and the interrupted first attempt always run with it
    rejected, and it is opened only after the v0.7.7 process is gone. This commit ships "blocked" so the smoke
    rehearsal registers nothing; the full run sets "allowed" (one config line). The node's address and public name are
    in the evidence. Stage A is always blocked.
  * linux-aarch64 is the named exception above; no stranded v0.7 install can consume it.
  * Before the Latest flip the real updater compares "=": it tries a "downgrade" to v0.7.11, gets 404 for
    arc-node-linux-x86_64 and exits 22. No state change. After the flip it reports "up to date".
  * One VM, one node, one run: this is a rehearsal of the field, not a statistical sample.

RESOURCES SUPPLEMENT (profile "resources"; ARC-83 independent review criteria D and E; Astra's decision of 2026-10-08T13:19Z)
Why: Wave 0 run 37750760170 (WAVE0_PASS, 4 h, VM 6144 MiB) recorded no per-sample RSS, available memory, swap or disk
series, no public scoreboard freshness and no kernel OOM scan. This run supplies exactly those, on the published
v0.7.12 launcher, with the live network, on a 4096 MiB VM (the 4 GiB canary criterion E is written for; the change from
6144 is disclosed in binding.json and in the report). It is combined evidence with run 37750760170; it does not repeat
the interruption, updater runs, kickstarts or reboot (those checks show as "covered by" rows).
  same bytes     binding.json holds, for this run and for 37750760170: launcher, node, legacy v0.7.7 node, v0.7.11
                 installer and cloud image sha256, the sha256 of the three units the installer wrote, and the
                 baseline-result line. This run's values are MEASURED from the real bytes during the run; the prior
                 values are the committed config stage_b.prior_run block (each read from that run's own evidence, with
                 its source named there). The evaluator compares them itself.
  window         consume, then 600 s settle, then a quiet window: first sample to last sample >= 135 min (8100 s),
                 >= 136 samples, no gap between adjacent samples above 65 s, nothing forced inside it. The run goes
                 three sample intervals past the nominal end so the window cannot fall short by sampler phase.
  samples        every 60 s, absolute schedule: node RSS/peak/swap, threads, fds, cpu seconds; MemTotal, MemAvailable,
                 swap; cgroup memory and swap; disk total and free of the data volume; bytes of data, release cache
                 and logs; largest file; partial files; bridge download log lines; the age of the last SUCCESSFUL
                 registration/heartbeat (registration_age_s) and its timestamp.
  local freshness a second guest observer polls the node's LOCAL /community/worker/status every 5 s (the next round is
                 scheduled 15 s after the previous one completes, so the period is 15 s plus the round's latency) and
                 logs every poll, failures included, to heartbeats.jsonl, so every distinct last_registration_unix_ms
                 is seen. Source: crates/arc-node/src/community_worker.rs:156-164 (stamp set only when a coordinator
                 accepted), main.rs:9181 (once per round), main.rs:9183 (next round 15 s later), main.rs:5595 (15 s),
                 main.rs:9103 (registration every 4th tick).
  public freshness the runner (not the VM) reads GET /workers/scoreboard?worker_id=0x<address> on all six coordinators
                 every 30 s, in parallel, keeping per coordinator the HTTP status, the server's Date header, count_total
                 and our row. The node serves a row only while its last heartbeat is within 90 s (rpc.rs:784, handler
                 rpc.rs:8470, filter rpc.rs:8514). Read-only; /community/list is never called; the evidence stores an
                 index and a short hash for each coordinator, never its address. Missing coverage is UNPROVED, never PASS.
  kernel         the journal of every boot of the guest is scanned for out-of-memory kills over the whole run
                 (kernel-oom.json); any kill fails.
  bounds         RSS slope <= 100 MiB/h; MemAvailable >= 512 MiB; 24 h projection <= half of the headroom; disk reserve
                 max(2 GiB, 20% of the volume) never reached and a 72 h runway if free space falls; swap is a series only;
                 no unbounded log or cache growth, no second full binary download, no model-sized download.
  verdict        SUPPLEMENT_PASS / SUPPLEMENT_FAIL. SUPPLEMENT_PASS is evidence to be read together with run
                 37750760170; it never stands in for the four-hour Wave 0.
  stop           the job still ends with the final stop, rollback test and re-bridge, and the node stopped.
